# صفحة «حالة النسخ الاحتياطي» — بيانات حقيقية + سجل تحقق + تحسين الواجهة

الصفحة حالياً ثابتة بالكامل: كل القيم مكتوبة يدوياً في الكود، ولا تحفظ أي شيء، ولا تحتوي زر رجوع ولا حارس صلاحيات، وألوانها مكتوبة كقيم صريحة بدل رموز التصميم.

## 1) ربط الصفحة ببيانات حقيقية

بطاقات مؤشرات تُقرأ فعلياً من قاعدة البيانات بدل القيم الثابتة:

- حجم قاعدة البيانات الحالي، وعدد الجداول في المخطط العام.
- عدد كائنات التخزين وحجمها الإجمالي لكل bucket (مرفقات الطلبات وسندات الدفع والوثائق)، لأن هذه هي الأصول التي يجب أن تشملها النسخة.
- آخر migration مطبقة (المعرّف والتاريخ) كمؤشر على آخر تغيير بنيوي.
- آخر نشاط مكتوب في النظام (أحدث سجل تدقيق) لتقدير حجم فقد البيانات المحتمل.
- آخر عملية تحقق يدوي مسجّلة ونتيجتها، ومنذ كم يوماً (مع تلوين تحذيري إذا تجاوزت المدة المحددة).

ما يبقى «يحتاج تأكيد يدوي» فقط هو ما لا يمكن قراءته فعلاً: تاريخ آخر نسخة احتياطية ناجحة وحالة PITR. سيتم توضيح ذلك بجملة دقيقة بدل التنبيه العام الحالي، ولن يُعرض أي رقم مُختلق.

## 2) سجل التحقق اليدوي (قابل للحفظ)

بدل النص «— غير مسجّل —»:

- نموذج تسجيل عملية تحقق: التاريخ، نوع الفحص (نسخة/PITR/اختبار استرجاع/فحص التخزين)، النتيجة (ناجح/ناجح مع ملاحظات/فاشل)، RTO وRPO المرصودان، ملاحظات، والمسؤول.
- جدول بآخر عمليات التحقق مع إمكانية العرض والفلترة، وتثبيت آخر نتيجة أعلى الصفحة.
- قائمة فحص الاسترجاع الستة تصبح بنوداً قابلة للتعليم ضمن عملية التحقق، ويظهر لكل بند تاريخ آخر مرة تم فيها.
- الكتابة مقيدة بدور system_admin / admin فقط، مع تسجيل العملية في سجل التدقيق. لا يمكن تعديل أو حذف سجل سابق (append-only).

## 3) إصلاحات الصفحة وتحسين التصميم

- إضافة زر الرجوع للخلف المستخدم في بقية الصفحات.
- إضافة حارس الصلاحيات ورسالة «لا تملك صلاحية» بدل صفحة فارغة أو خطأ خام.
- استبدال الألوان الصريحة (amber/emerald) برموز التصميم الدلالية المعتمدة في المشروع.
- إعادة ترتيب الصفحة: شريط حالة أعلى (جاهز / يحتاج تحقق / متأخر)، ثم بطاقات المؤشرات، ثم قائمة الفحص، ثم سجل التحقق.
- توحيد المصطلحات بالعربية وضبط اتجاه RTL للأرقام والتواريخ.

## تفاصيل تقنية

- ملف جديد `src/lib/admin-backup-status.functions.ts` بنمط `createServerFn` + `requireSupabaseAuth` + `assertAnyRole`، على غرار `admin-system-readiness.functions.ts`، ويضم: `getBackupStatusOverview` و`listBackupVerifications` و`recordBackupVerification`.
- المقاييس تُقرأ عبر دوال قراءة آمنة (حجم القاعدة، `storage.objects` مجمّعة، ledger الـmigrations، أحدث سجل تدقيق) بلا كشف بيانات حساسة.
- الواجهة: `useQuery` / `useMutation` مع `useServerFn`، وإبطال المفاتيح بعد التسجيل.
- مكوّنات جديدة تحت `src/components/admin/backup/` لإبقاء ملف المسار صغيراً.

## نقطة توقف تتطلب موافقتك

حفظ سجل التحقق يحتاج جدولاً جديداً (`backup_verifications`) مع GRANT وRLS وسياسات مقيدة بالدور — أي **migration إنتاجية**. قواعد المشروع الحالية تمنع تطبيق migrations دون تصريح صريح، والتصريح المؤقت السابق انتهى.

الخيارات:
1. تصرّح بتطبيق migration واحدة لهذا الجدول فقط (مضافة، بلا مساس بأي جدول قائم) — عندها ينفَّذ البند 2 كاملاً.
2. أنفّذ البندين 1 و3 الآن (بيانات حقيقية + إصلاحات وتصميم)، ويبقى سجل التحقق للعرض فقط حتى تصرّح لاحقاً.
