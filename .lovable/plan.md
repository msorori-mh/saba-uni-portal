# المسار الأول — مشاريع التخرج (GP)

## GP-1 إغلاق المصدر على main الحالي
- إزالة عنصر «مرشحو التخرج» من قائمة الإدارة مع إبقاء المسار والبيانات، وإزالة روابطه من لوحة التنفيذيين ولوحة الإدارة.
- إضافة واجهة إنشاء فريق المشروع للطالب المؤهل (المستوى الرابع فقط) فوق `create_graduation_project_team` الموجود، مع إضافة/إزالة الأعضاء واحترام قيد «فريق نشط واحد».
- ربط ملف تقرير التقدم بالتقرير نفسه عند الرفع (منع الملفات اليتيمة).
- تمرير ملاحظات القرار النهائي عبر المسار بعد تطبيق هجرة GP-2.
- الإشراف الإداري يبقى قراءة فقط بلا أي صلاحية تشغيلية للأدمن/العميد/المسجل؛ المنسق يبقى محصوراً بقسمه.

## GP-2 الهجرات (بعد إثبات الغياب أعلاه)
1. `20260811010000` — خيارات الهوية وملاحظات القرار.
2. `20260811020000` — معالجة نتائج التدقيق الأمني المستقل لـGP.
تُطبَّق كل واحدة منفردة، مع تحقق بعدي للكائنات والصلاحيات وRLS، وبلا أي مساس بـB1 أو شهادة القيد أو المجالس.

## GP-3 التحقق و E2E
- مصفوفة تفويض إيجابية/سلبية على مستوى RPC: طالب مستوى رابع، طالب غير مؤهل، منسق داخل قسمه، منسق خارج قسمه، مشرف، عضو لجنة، أدمن/عميد/مسجل (قراءة فقط).
- E2E: فريق → مقترح → إشراف → تقدم → تسليم نهائي → مناقشة → تقييم → «مطلوب تعديل» → إعادة تقييم → قرار → أرشفة، مع إثبات رفض الأرشفة قبل الحالة النهائية.
- تُستخدم حسابات TEST_ONLY موسومة ضمن حزمة محكومة بعقد عزل وتنظيف، بلا حسابات وهمية دائمة.

# المسار الثاني — شؤون الخريجين (GA)

## GA-1 إغلاق المصدر
- استكمال مسار الطالب/الخريج والموظف فوق AUTH-04 دون أي منطق مرتبط باسم موظف.
- إضافة صفحة إشراف إداري `/admin/graduates-affairs` للقراءة فقط: مؤشرات مجمّعة بلا بيانات شخصية، مع حالات تحميل/فراغ/خطأ، ومحمية بفحص صلاحية واضح.
- ربط مجموعة «شؤون الخريجين» في قائمة الإدارة بهذه الصفحة.

## GA-2 الهجرة
- `20260811230000` — دالة التحقق من إجابات الاستبيان (داخلية غير قابلة للاستدعاء من العملاء)، تشديد حدود جمهور الفعاليات، وتوحيد سياق الخريج المعتمد الواحد.

## GA-3 تهيئة النطاق (بيانات تهيئة فقط، بنية عامة)
- بنية النطاق تبقى: تعيين معالجة → ملف موظف → `staff_profile_departments` (many-to-many عام).
- ربط المختص الحالي بقسمه من داخل صفحة الهيكل التنظيمي كبيانات تهيئة، بحيث يدعم النظام لاحقاً مختصاً لعدة أقسام أو عدة مختصين لقسم واحد دون تعديل مصدر.
- إنشاء سياسة استمرارية الحساب المعتمدة للقدرات المطلوبة (بدونها كل الخدمات مرفوضة).
- الأقسام والبرامج تُقرأ من قاعدة البيانات وفق الحقيقة التنظيمية المعتمدة (علوم الحاسوب: علوم الحاسوب + الذكاء الاصطناعي؛ تكنولوجيا المعلومات: تكنولوجيا المعلومات + الأمن السيبراني؛ نظم المعلومات الحاسوبية: نظم المعلومات الحاسوبية) دون ترميزها في الكود.

## GA-4 التحقق و E2E
- مصفوفة تفويض: خريج (سجله المعتمد فقط)، مدير (نطاق الكلية)، مختص داخل قسمه، مختص خارج قسمه (رفض)، مختص بلا قسم (رفض)، أدمن/عميد/مسجل (قراءة فقط بلا تجاوز تشغيلي).
- E2E محكوم بحساب اختباري موسوم: سجل خريج معتمد تجريبي → وسائل تواصل → موافقة → تسجيل وظيفي → فرصة/فعالية → استبيان → متابعة → تقرير مجمّع، ثم تنظيف.

- تفعيل العلمين `studentGraduatesAffairs` و`staffGraduatesAffairs` معاً فقط بعد نجاح كل المصفوفات.
- CI كامل: كل اختبارات bun، فحص الأنواع، البناء، diff-check، والمدقّقات المتاحة — Critical = 0 و High = 0.
- فحص عدم الانحدار: المجالس، B1، شهادة القيد، التقارير.
- تجميد SHA النهائي → نشر → التحقق من `/version.json` ومطابقة SHA المنشور للمصدر المقبول اليوم → E2E إنتاجي في المتصفح → مصفوفة سلبية أمنية نهائية.
- التقرير الختامي يصدر بالحقول المطلوبة كاملة (CURRENT_MAIN_SHA … FINAL_DECISION).
