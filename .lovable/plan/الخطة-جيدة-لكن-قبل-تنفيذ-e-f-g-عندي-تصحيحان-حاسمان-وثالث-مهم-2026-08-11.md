# الخطة جيدة، لكن قبل تنفيذ E→F→G عندي **تصحيحان حاسمان** وثالث مهم؛ وإلا قد نغلق الـLegacy ثم نكسر الطلبات القديمة.

أخطر نقطة هي هذه: الطلبات القائمة مثبتة على **Version 1**، بينما `action_code` في تعريفات V1 كان فارغًا وكان التنفيذ يعتمد على القائمة البيضاء القديمة. لذلك لا يجوز في G جعل `LEGACY_FALLBACK_ENABLED=false` عالميًا قبل إثبات أحد الأمرين: إما أن عدد الطلبات النشطة على V1 أصبح صفرًا، أو أن V1 أصبح له **Historical Runtime Contract** كامل يمكن للمحرك الجديد تنفيذه دون الرجوع إلى القائمة القديمة. الأفضل الثاني: إنشاء Snapshot توافق غير قابل للتعديل لكل خطوات V1 يتضمن `step_key + unit + role + scope + action_code + transitions + final effect`، مرتبطًا بـV1، من دون تغيير بيانات الطلبات القائمة أو إعادة تثبيتها على V2.

ثانيًا، إصلاح `can_current_user_act_on_step` صحيح من حيث المبدأ، لكن لا أريد دالة التفويض تعدّ الانتقالات ثم يقوم المنفذ بحسمها مرة أخرى بمنطق منفصل. يجب أن يكون هناك **Resolver واحد authoritative**:

```text
authorize actor
→ resolve transition once
→ obtain exact transition_id
→ execute the same resolved transition

```

وكل ذلك داخل العملية الذرية نفسها. إذا كان صفر انتقالات أو أكثر من انتقال صالح بنفس الأولوية أو Default غير حاسم → DENY/HOLD. هذا يمنع اختلاف قرار التفويض عن قرار التنفيذ.

ثالثًا، لا أنصح بإنشاء `legacy_fallback_calls` كعداد يُكتب في قاعدة الإنتاج مع كل طلب، ولا بتخزين نتائج المصفوفة الدائمة في الإنتاج لمجرد الإثبات. هذا يضيف Writes تشغيلية لا نحتاجها. الأفضل أن تكون مصفوفة الأدلة كاملة في بيئة الـexact rehearsal، وفي الإنتاج — إذا أذنت باختبار إنتاجي لاحقًا — نستخدم TEST_ONLY وAudit الموجود أصلًا أو transaction-safe verification، ونثبت أن Legacy غير reachable عبر اختبارات المصدر + الـruntime contract + عدم وجود أحداث Legacy. **أي Positive RPC matrix على الإنتاج نفسها تعتبر كتابة إنتاجية وتحتاج إذنك الصريح قبل التنفيذ.**

بعد هذه التصحيحات أعتمد التسلسل:

```text
E0  إصلاح resolver الموحد
E1  Historical contract لـ V1
E2  Full V2 authorization matrix خارج الإنتاج
E3  حسم ROUTE_SEMANTIC_SHA256 + جميع الاختبارات خضراء

F1  Cutover enrollment_suspension
F2  excused_absence
F3  file_withdrawal
F4  department_transfer
F5  final_chance

G1  إثبات أن كل V1/V2 request قابل للتنفيذ بدون whitelist
G2  تعطيل Legacy لكل الخدمات
G3  إثبات legacy reachable paths = 0
G4  Full regression + closure report

```

وشرط الإغلاق أضيف له سطرين مهمين:

```text
ACTIVE_V1_REQUESTS_SUPPORTED_WITHOUT_LEGACY=YES
RUNTIME_TRANSITION_RESOLVER_SINGLE_SOURCE=YES

```

إضافةً إلى الشروط السابقة:

```text
PUBLISHED_SERVICES=5/5
CONFIG_SOURCE_OF_TRUTH=YES
PARITY=100%
RPC_POSITIVE_MATRIX=PASS
RPC_NEGATIVE_MATRIX=PASS
LEGACY_RUNTIME_ACTIVE=NO
ROUTE_SEMANTIC_TEST=PASS
FULL_TEST_SUITE=PASS

```

**القرار: تابع E→F→G، لكن بعد معالجة V1 والـsingle resolver أولًا.** هذه ليست تحسينات اختيارية؛ خصوصًا V1 لأنها قد تتحول إلى عطل حقيقي للطلبات الجارية عند إيقاف الـLegacy.E → F → G: جعل التعريف مصدر الحقيقة الوحيد للخدمات الطلابية

## 0. عائق مؤكد يجب إصلاحه قبل E (اكتُشف بالفحص الآن)

دالة التفويض `can_current_user_act_on_step` تشترط، لطلبات B1، وجود **انتقال واحد بالضبط** من الخطوة الحالية يطابق نتيجة الإجراء:

```text
SELECT count(*) ... WHERE from_step_id = current AND action_result matches action
RETURN v_transition_count = 1;
```

بعد إضافة تفرّع الرسوم في الإصدار 2، أصبح لدى `dean_approval` (تحويل القسم) و`dean_decision` (الفرصة الأخيرة) **انتقالان** بنتيجة `approved` (مسار برسوم + مسار افتراضي بلا رسوم). النتيجة: أي طلب جديد مثبّت على الإصدار 2 سيُرفض عند خطوة العميد بخطأ تفويض.

الإصلاح (Migration forward-only، أول خطوة في E): تعديل الشرط ليصبح «يوجد على الأقل انتقال واحد مطابق، ويُحسم بواسطة `resolve_b1_workflow_transition` إلى انتقال واحد فقط» بدل «واحد بالضبط»، مع الإبقاء على الرفض عند صفر انتقال أو عند تعدد غير قابل للحسم.

## 1. الحادثة والاختبار الأحمر (شرطان قبل الإغلاق)

- **حادثة سياق الأهلية**: توثيق رسمي في `docs/incidents/INC-2026-08-11-eligibility-context-helper.md` (السبب: نشر نسخة تستدعي `get_student_request_eligibility_context_v1` غير موجودة؛ الأثر: أي فحص أهلية كان سيفشل؛ الاكتشاف والإصلاح خلال دقائق بترحيل استعادة كامل). لا تعديل على أي migration مطبقة، والإصلاح موجود أصلًا كترحيل مستقل forward-only. يُضاف ترحيل تحقّق (verifier) يثبت أن الدالة تُرجع كل الحقول المطلوبة، ويُسجّل الناتج كدليل.
- `**ROUTE_SEMANTIC_SHA256**`: أولًا نثبت مشروعية الانحراف — مقارنة شجرة المسارات الحالية بالبصمة المثبتة وتحديد المسارات المضافة (أرشيف المجالس، سياسات مشاريع التخرج، …). إذا كانت كل الفروق مسارات أضفناها عمدًا وموثقة، تُحدَّث البصمة في الاختبار مع تعليق يذكر سبب التحديث. إذا ظهر أي مسار غير مقصود أو ازدواج، يُصلح المصدر ولا تُحدَّث البصمة.

## 2. E — مصفوفة التفويض للإصدار 2

**خارج الإنتاج أولًا**: مشروع/قاعدة نظير تُبنى من `supabase/migrations` كاملة، وتُولَّد فيها بيانات فاعلين اصطناعية (وحدات، أدوار، تعيينات) وطلبات لكل خدمة. تُنفذ المصفوفة كاملة عبر استدعاء RPC مباشرة بهوية كل فاعل — لا اعتماد على الواجهة.

لكل خدمة × كل خطوة:

- **إيجابي**: الدور + الوحدة + النطاق + المكلّف + `action_code` + الخطوة الحالية → ALLOW.
- **سلبي**: دور خاطئ، وحدة خاطئة، نطاق خاطئ (قسم آخر في خطوتي رئيس القسم)، مكلّف آخر، `action_code` خاطئ، خطوة غير حالية، خطوة قديمة (stale/completed)، سابقة غير مكتملة، إصدار workflow مختلف، اقتران خدمة/إجراء غير صحيح → DENY.
- **إلزامي**: admin غير مكلّف → DENY، dean غير مكلّف → DENY، registrar غير مكلّف → DENY.
- **تفرّع الرسوم**: رسوم > 0 → `payment_confirmation` مطلوبة؛ لا رسوم → تُسجَّل `skipped` والمسار ينتقل إلى `registrar_apply`؛ محاولة تنفيذ `payment_confirmation` بعد `skipped` → DENY.

النتائج تُخزَّن في جدول أدلة `b1_authorization_matrix_results` (حالة، خدمة، خطوة، فاعل، نتيجة متوقعة/فعلية، رمز الخطأ) مع بصمة تشغيل واحدة.

**ثم الإنتاج**: نفس المصفوفة بحزمة مضبوطة على طلبات موسومة TEST_ONLY فقط وحسابات اختبار قائمة، بدون مساس بالسجلات المحمية. أي تجاوز صلاحية = توقف فوري، إصلاح، ثم إعادة المصفوفة كاملة للخدمات الخمس.

## 3. F — Cutover خدمة تلو الأخرى

الترتيب: `enrollment_suspension` → `excused_absence` → `file_withdrawal` → `department_transfer` → `final_chance`.

لكل خدمة، قبل الانتقال للتالية، يُثبَت أن Runtime يتحقق من: الإصدار المنشور المثبّت على الطلب، `step_key`، وحدة المعالجة، الدور المطلوب، النطاق، `action_code`، والانتقال المحسوم — وأن المسار الطبيعي **لا يستشير** قائمة الـ25 المثبتة في `is_valid_b1_runtime_step_contract`.

آلية التنفيذ: علم تشغيل `LEGACY_FALLBACK_ENABLED` في جدول إعدادات المنصة، مقروء داخل الدوال، بقيمة لكل خدمة. عند تحويل خدمة إلى Config Runtime يصبح فحص القائمة القديمة **غير مستدعى** في مسارها، ويُستبدل بفحص مشتق من الإعداد المنشور. كل استدعاء للمسار القديم يُسجَّل في عدّاد `legacy_fallback_calls` لإثبات الصفر لاحقًا. دورة حياة كل طلب جارٍ تبقى على إصدارها المثبّت.

## 4. G — تعطيل Legacy

بعد نجاح E وF لكل الخدمات: `LEGACY_FALLBACK_ENABLED=false` عالميًا، ثم إعادة تشغيل المصفوفة الكاملة وE2E مختصر لكل خدمة لإثبات:

- `legacy_fallback_calls = 0`
- 100% من قرارات التفويض والانتقال مشتقة من الإعداد المنشور

يبقى كود التوافق موجودًا لكن غير قابل للوصول، ويُحذف لاحقًا في تنظيف مستقل (migration + source) خارج هذه الجولة.

## 5. شرط الإغلاق

يُصدر تقرير نهائي بالقيم المطلوبة، ولا يُعلن PASS إلا بتحقق كل السطور:

```text
PUBLISHED_SERVICES=5/5   CONFIG_SOURCE_OF_TRUTH=YES  CONDITIONAL_BRANCHING=PASS
ELIGIBILITY_CATALOG=PASS PARITY=100%                 RPC_POSITIVE_MATRIX=PASS
RPC_NEGATIVE_MATRIX=PASS ADMIN_BYPASS=DENY           DEAN_BYPASS=DENY
REGISTRAR_BYPASS=DENY    LEGACY_RUNTIME_ACTIVE=NO    LEGACY_FALLBACK_CALLS=0
ROUTE_SEMANTIC_TEST=PASS FULL_TEST_SUITE=PASS
```

## التفاصيل التقنية

- Migrations (forward-only، واحدة في كل مرة مع preflight/post-verify): (1) حسم الانتقال المتعدد في `can_current_user_act_on_step`؛ (2) جدول أدلة المصفوفة + دوال تسجيل؛ (3) جدول علم `LEGACY_FALLBACK_ENABLED` وعدّاد الاستدعاءات؛ (4) اشتقاق فحص العقد من الإعداد المنشور بدل القائمة المثبتة، مع مسار قديم مشروط بالعلم.
- ملفات المصدر: مشغّل المصفوفة تحت `scripts/b1/authorization-matrix/`، اختبارات ثابتة تحت `tests/student-requests/service-platform/`، تحديث بصمة المسارات في `tests/student-requests/tanstack-register-stable-augmentation-01.test.ts` بعد إثبات المشروعية، وتقرير الأدلة تحت `docs/reviews/`.
- بعد الإغلاق مباشرة: تطبيق نفس الأساس (إصدارات منشورة + كتالوج إجراءات آمنة + سياسات قابلة للتهيئة + مصفوفة تفويض) على مشاريع التخرج وشؤون الخريجين، كل نظام على حدة.
