## 1) القرار

**NEEDS_USER_INPUT** — البيانات **عددياً** كافية لأدوار المجالس (chairs، secretaries، members، admin)، لكن تقرير الجاهزية **لا يحدد** حسابات اختبار بعينها (بريد، رقم وظيفي، `user_id`، أو ربط شخص ↔ مجلس). لا يمكن تنفيذ smoke test للمجالس/الاجتماعات/جدول الأعمال **بدون تحديد صريح من الأدمن** لحساب واحد لكل دور.

**لماذا ليس PASS:** معيار النجاح يتطلب حسابات **واضحة** لـ admin وchair وsecretary/member دون طلب بيانات إضافية — غير متحقق.

**لماذا ليس NO-GO:** العضويات والأدوار **موجودة** (11 عضوية نشطة، 4 مجالس، 4 admin) — المشكلة **تعيين الهوية** وليس غياب البنية.

## 6) Checklist اختبارات لكل دور (للتنفيذ لاحقاً)

### admin / system_admin

- [ ] دخول لوحة الإدارة (`/admin/login`)
- [ ] فتح `/admin/academic-councils`
- [ ] اختيار مجلس (كلية أو قسم)
- [ ] جدولة اجتماع واحد (`scheduleCouncilMeeting`)
- [ ] فتح قسم «جدول الأعمال» واختيار الاجتماع
- [ ] إضافة موضوع `accepted_for_agenda` أو بند يدوي
- [ ] ترتيب البنود
- [ ] اعتماد جدول الأعمال (`finalizeMeetingAgenda`)

### chair

- [ ] دخول `/faculty-portal` بحساب chair
- [ ] رؤية مجلسه/مجالسه في «مجالسي الحالية»
- [ ] قسم «جدولة اجتماع (رئيس المجلس)» — مجلسه فقط
- [ ] جدولة اجتماع لمجلس يرأسه
- [ ] قسم «جدول الأعمال» — إضافة/ترتيب/تعديل
- [ ] زر «اعتماد جدول الأعمال» يظهر ويعمل
- [ ] **لا** إدارة مجلس لا يرأسه (عزل `council_id`)

### secretary

- [ ] دخول faculty بحساب secretary
- [ ] رؤية مجلسه
- [ ] محرر جدول الأعمال: إضافة/ترتيب/تعديل
- [ ] **لا** يظهر زر «اعتماد جدول الأعمال»
- [ ] **لا** `agenda_ready` عبر واجهته

### member

- [ ] رؤية الاجتماعات القادمة/السابقة
- [ ] توسيع «جدول الأعمال» في بطاقة الاجتماع (قراءة فقط)
- [ ] تقديم موضوع (`submitCouncilTopic`)
- [ ] رفع مرفق لموضوع
- [ ] **لا** محرر أجندة ولا اعتماد

### viewer

- [ ] قراءة المجلس والاجتماعات والأجندة
- [ ] **لا** نموذج تقديم موضوع
- [ ] **لا** جدولة ولا تعديل اجتماع/أجندة  
- *(يتطلب إنشاء عضوية viewer أولاً — غير متوفر حالياً)*

### student (اختياري — Pilot يشمل بوابة الطالب)

- [ ] دخول `/student` برقم أكاديمي
- [ ] عرض البيانات الأساسية (ملف، برنامج، قسم)
- [ ] **لا** وصول لمجالس أو admin

## 7) ما يجب على الأدمن تجهيزه يدوياً قبل الاختبار

### أ. تحديد حسابات الاختبار (إلزامي)

| # | المطلوب | مثال الحقل (بدون كلمات مرور) |
|---|---------|-------------------------------|
| 1 | بريد أو معرّف **admin/system_admin** واحد للمختبر | `admin@...` أو حساب staff معروف |
| 2 | **رئيس مجلس الكلية** — بريد faculty + تأكيد عضوية `chair` | `Fxxxx@faculty.usr.edu.ye` |
| 3 | **رئيس مجلس قسم واحد** (يُفضّل CS أو IS لوجود secretary+member) | نفس النمط + قسم CS/IS/IT |
| 4 | **أمين سر** لنفس مجلس القسم أو مجلس آخر | عضوية `secretary` |
| 5 | **عضو عادي** في مجلس فيه member (ليس IT حتى يُضاف member) | عضوية `member` |
| 6 | **viewer** (اختياري — موصى به) | إنشاء عضوية `viewer` لشخص واحد عبر `/admin/academic-councils` |
| 7 | **طالب اختبار** (اختياري) | رقم أكاديمي + تأكيد وجود بريد إن لزم reset |

### ب. تأكيد الربط (إلزامي)

- [ ] كل حساب له **حساب دخول فعّال** (`auth.users` + profile نشط)
- [ ] كل حساب faculty مربوط بـ **`faculty_profiles.user_id`**
- [ ] عضويات **`academic_council_members`** نشطة (`is_active=true`, `active_to` null) بالأدوار الصحيحة
- [ ] التحقق من **مجلس الكلية**: chair + (يفضل إضافة secretary قبل اختبار سير كامل)
- [ ] التحقق من **مجلس IT**: إضافة **member** واحد على الأقل إن رُغب اختبار member من قسم IT

### ج. تسليم للمختبر (بدون كلمات مرور في التقرير)

- [ ] توفير `.env` محلي أو جدول آمن منفصل يحتوي: `ADMIN_EMAIL`، `CHAIR_COLLEGE_EMAIL`، `CHAIR_DEPT_EMAIL`، `SECRETARY_EMAIL`، `MEMBER_EMAIL` — **كلمات المرور خارج التوثيق**
- [ ] أو تسليم كلمات مرور مؤقتة عبر قناة آمنة (لا تُوثَّق في docs)

### د. بيانات تشغيل للمجالس smoke (يُنشأ أثناء الاختبار — لا seed)

- [ ] اجتماع **واحد** لكل مجلس مراد اختباره (أو اجتماع واحد كحد أدنى)
- [ ] موضوع بحالة `accepted_for_agenda` لاختبار إضافة للأجندة (أو مراجعة الموضوعين الـ 2 الموجودين)
