## HIGH

### H-01 — GP `revisions_required` does not create a new decision/evaluation boundary

**ID:** H-01
**Severity:** HIGH
**System:** GP
**Exploitability:** Authenticated coordinator with access to a project that has a held defense and a complete prior evaluation set; directly callable RPC path, no UI dependency.
**Production relevance:** Yes — a later graduation result can be based on stale pre-correction committee evidence. No production traffic was generated by this audit.
**PR340 / PR341 already fix this:** PR340: No evidence in the reviewed checkout. PR341: No evidence in the reviewed checkout. Finding remains open.

**SYSTEM**
Graduation Projects — final submission, supervisor review, committee evaluation, and graduation result.

**FILE/FUNCTION**
`supabase/migrations/20260807001114_c22e6009-1472-43ef-9443-b002872bbba5.sql`
`public.submit_graduation_project_final` (lines 375–401), `public.review_graduation_project_final` (403–435), `public.conclude_graduation_project_result` (569–598).

**ATTACK/FAILURE PATH**
1. A coordinator directly calls `conclude_graduation_project_result(..., 'revisions_required', ...)` after the held defense has a complete submitted evaluation set.
2. The project remains in lifecycle state `evaluating`; only `final_decision` changes.
3. The student submits a replacement final file and the supervisor marks it ready.
4. The coordinator directly calls `conclude_graduation_project_result(..., 'passed'|'failed', ...)` again.

**EXPECTED**
`revisions_required` must be a correction round. A new corrected final must be submitted and reviewed, and the decision must require a fresh or explicitly versioned evaluation/defense set. Stale evaluations from the pre-correction round must not authorize a new final decision.

**ACTUAL**
The submit/review functions explicitly allow the old `evaluating` state when `final_decision = 'revisions_required'`. The conclude function only checks `lifecycle_state = 'evaluating'`, a held discussion, and `submitted_count = panel_count`; it does not require a post-correction evaluation round or bind evaluations to a correction/final version. The same old submitted evaluations therefore authorize the subsequent passed/failed decision.

**EVIDENCE**
- `submit_graduation_project_final`: lines 389–391 allow submission when `p.final_decision` is `revisions_required` without a lifecycle transition.
- `review_graduation_project_final`: lines 419–429 allow review in the same state and only require a current clean file plus any `final_submitted` event for that file.
- `conclude_graduation_project_result`: lines 583–590 require only `evaluating`, a held discussion, and all panel evaluations submitted; lines 591–596 average the submitted evaluations and update the decision.
- The E2E test description mentions a corrected-final branch, but no executable negative test proves that stale committee evaluations cannot be reused.

**RECOMMENDED MINIMAL FIX**
Add an explicit correction-round/version boundary. On `revisions_required`, invalidate or version the prior evaluation set; require a post-correction final submission and supervisor readiness; then require a new defense/evaluation set, or an explicitly authorized re-review set tied to the new round, before allowing `passed` or `failed`. Add a direct-RPC negative PostgreSQL test proving stale evaluations are rejected.

### H-02 — GA event registration bypasses event audience authorization

**ID:** H-02
**Severity:** HIGH
**System:** GA
**Exploitability:** Any approved graduate who can supply a published future event UUID and valid self/consent IDs can call the authenticated registration RPC directly; UI filtering is not required.
**Production relevance:** Yes — an out-of-program or out-of-department graduate can create an event registration. No production traffic was generated by this audit.
**PR340 / PR341 already fix this:** PR340: No evidence in the reviewed checkout. PR341: No evidence in the reviewed checkout. Finding remains open.

**SYSTEM**
Graduates Affairs — graduate self-service event participation.

**FILE/FUNCTION**
`supabase/migrations/20260810162735_d239a40c-83fa-4f0d-95b2-be9ab4cfc284.sql`
`public.graduate_register_for_event` (lines 852–892); comparison predicate `public.graduate_audience_matches` (lines 430–449); `public.graduate_list_visible_events` (lines 985–994).

**ATTACK/FAILURE PATH**
An approved graduate calls the granted RPC directly with the UUID of a published future event scoped to another program or department. The graduate supplies a valid self record and consent ID. The event is hidden by the list RPC, but the caller can obtain or guess the UUID from an allowed backend/client surface and submit a registration.

**EXPECTED**
The write RPC must enforce the same publication and audience predicate as event listing. Hidden or out-of-audience events must be rejected regardless of UI visibility.

**ACTUAL**
`graduate_register_for_event` checks authentication, self ownership, approved-record lock, and `published AND starts_at > now()`, then inserts the registration. It never calls `graduate_audience_matches` or otherwise checks the event audience. `graduate_list_visible_events` does apply `graduate_audience_matches`, so the authorization boundary differs between read/list and direct write.

**EVIDENCE**
- Registration function lines 869–878 contain self/approved/open checks only.
- Insert occurs at lines 880–885 with the caller-supplied event ID.
- List RPC applies `graduate_audience_matches` at lines 985–994.
- Existing SQL tests verify the list predicate but do not include a direct-RPC cross-audience registration denial case.

**RECOMMENDED MINIMAL FIX**
In `graduate_register_for_event`, join the event to the caller’s approved graduate record and require `graduate_audience_matches(e.audience_scope, r.program_id, r.department_id)` before insertion. Return a dedicated denial error and add an out-of-audience direct-RPC negative test.

### H-03 — GP coordinator assignment controls have no candidate data and cannot complete the core journey

**ID:** H-03
**Severity:** HIGH
**System:** GP
**Exploitability:** Any authorized coordinator using the portal encounters empty candidate lists; this is a deterministic availability failure rather than an identity bypass.
**Production relevance:** Yes — valid GP projects cannot progress through the portal without hidden/manual assignment preparation. No production traffic was generated by this audit.
**PR340 / PR341 already fix this:** PR340: No evidence in the reviewed checkout. PR341: No evidence in the reviewed checkout. Finding remains open.

**SYSTEM**
Graduation Projects — coordinator team/supervisor/committee operations.

**FILE/FUNCTION**
`src/routes/-graduation-projects-adapter.ts` `mapDetail` (lines 142–257).
`src/components/graduation-projects/MvpProjectWorkspace.tsx` (member, committee, and supervisor controls at lines 156–167, 465–475, and 617–628).

**ATTACK/FAILURE PATH**
After a coordinator creates or opens a valid project, the coordinator attempts to add a student, assign a supervisor, and assign the committee through the portal. Direct RPC authorization is present, but the UI has no scoped candidates to submit.

**EXPECTED**
The coordinator journey must load server-derived candidates constrained to the project processing department/role, or explicitly expose a safe, actionable blocked state. A project must be able to progress from accepted proposal through supervisor, committee, defense, evaluation, and result without manually seeded hidden assignments.

**ACTUAL**
`mapDetail` unconditionally returns empty arrays for `coordinatorOptions.supervisors`, `.committee`, and `.students`. The three UI controls consume those arrays, so the selects cannot produce IDs and the actions remain disabled. No adapter/RPC source method for these candidate lists was found in the reviewed runtime path.

**EVIDENCE**
- Adapter lines 252–256: all three candidate arrays are `[]`.
- Member add consumes `.students` at lines 156–167.
- Committee assignment consumes `.committee` and requires at least two IDs at lines 465–475.
- Supervisor assignment consumes `.supervisors` at lines 617–628.
- The backend lifecycle requires these assignments before later stages can progress.

**RECOMMENDED MINIMAL FIX**
Add read-only, server-authorized candidate RPCs or a scoped candidate projection to the detail RPC, keyed to the exact project department and processing role. Map the result into the three option lists and add a complete coordinator journey test plus cross-department negative cases. Do not populate these lists with client-provided or synthetic identities.

### M-02 — GP detail payload makes committee/evaluation readiness inaccurate

**ID:** M-02
**Severity:** MEDIUM
**System:** GP
**Exploitability:** Any authorized coordinator can receive an inaccurate readiness display when the actual panel size differs from the adapter fallback; the backend remains the final gate.
**Production relevance:** Yes — coordinators can miss or misunderstand the graduation decision action, creating incomplete or misleading operational processing. No production traffic was generated by this audit.
**PR340 / PR341 already fix this:** PR340: No evidence in the reviewed checkout. PR341: No evidence in the reviewed checkout. Finding remains open.

**SYSTEM**
Graduation Projects — coordinator readiness and committee display.

**FILE/FUNCTION**
`supabase/migrations/20260808010000_gp_student_level4_only_eligibility_guard_01.sql` `public.get_graduation_project_detail` (lines 359–420).
`src/routes/-graduation-projects-adapter.ts` `mapDetail` (lines 236–250); `src/components/graduation-projects/MvpProjectWorkspace.tsx` (lines 533–547).

**ATTACK/FAILURE PATH**
A project has a committee size different from two, or has more than two submitted evaluations. The coordinator relies on the detail screen to decide whether the result action is available.

**EXPECTED**
The detail contract must return authoritative `committee_count` and required evaluation count for the held discussion, and the UI must display/gate against those values.

**ACTUAL**
The SQL detail payload returns defense metadata without `committee_count`; its aggregate returns only `submitted_count` and `average_score`. The adapter maps missing committee count to `0` and missing required count to a hardcoded `2`. The UI therefore can hide a valid conclusion (for example 3/2) or show a misleading readiness state before the RPC rejects it.

**EVIDENCE**
- SQL lines 385–391 produce only `submitted_count` and `average_score`.
- SQL lines 413–414 produce defense ID/time/venue/state but no committee count.
- Adapter lines 240 and 249 default the missing values to `0` and `2`.
- UI lines 544–547 gates result controls on equality of those adapter values.

**RECOMMENDED MINIMAL FIX**
Return authoritative committee and required-evaluation counts from the detail RPC, map them without permissive defaults, and add tests for two-, three-, and incomplete-panel cases.

### M-05 — GA self context selects an arbitrary approved record instead of failing closed on ambiguity

**ID:** M-05
**Severity:** MEDIUM
**System:** GA
**Exploitability:** A user with multiple approved graduate records is deterministically bound to the newest record by `created_at`; the ambiguity cannot be resolved by the caller through this context RPC.
**Production relevance:** Yes — continuity and self-service capability routing can bind to the wrong program/record. No production traffic was generated by this audit.
**PR340 / PR341 already fix this:** PR340: No evidence in the reviewed checkout. PR341: No evidence in the reviewed checkout. Finding remains open.

**SYSTEM**
Graduates Affairs — account continuity and graduate self privacy/context binding.

**FILE/FUNCTION**
`supabase/migrations/20260810162735_d239a40c-83fa-4f0d-95b2-be9ab4cfc284.sql` `public.graduate_affairs_resolve_self_context` (lines 1464–1511).

**ATTACK/FAILURE PATH**
One authenticated user has two approved graduate records (for example, distinct programs or an erroneous duplicate). The self-context RPC is called by the UI and selects whichever record has the latest `created_at`; subsequent capability routing can therefore bind the session to the wrong graduate context.

**EXPECTED**
Self context must be deterministic and fail closed when more than one approved record is eligible, or explicitly return a safe, user-selected context without exposing unrelated records.

**ACTUAL**
The query filters by `sp.user_id` and `record_state = 'approved'`, orders by `created_at DESC`, and applies `LIMIT 1`. There is no count/uniqueness check and no ambiguity result. The database uniqueness index is per `(student_profile_id, program_id)`, so it does not itself guarantee one approved record per account.

**EVIDENCE**
- Lines 1483–1490 select the latest approved row and discard additional matches.
- Lines 1492–1495 evaluate continuity only after that arbitrary selection.
- Context tests cover no record and one approved record, but no two-approved-record fail-closed case.

**RECOMMENDED MINIMAL FIX**
Count eligible approved records and return `continuity_allowed=false` with no record ID unless exactly one row is eligible; alternatively require an explicit safe context selection with per-record authorization and audit. Add a two-approved-record negative test.

### L-01 — GP adapter promotes every project member to leader controls

**ID:** L-01
**Severity:** LOW
**System:** GP
**Exploitability:** Any ordinary project member can be shown leader controls when another team row is marked leader; backend authorization still blocks unauthorized mutations.
**Production relevance:** Limited — it creates misleading controls and avoidable denied actions, but no direct write bypass was found. No production traffic was generated by this audit.

**RECOMMENDED MINIMAL FIX**
Return the caller’s authoritative assignment/`is_leader` from the detail RPC, or compare the returned assignment user ID to the authenticated caller in the server adapter. Add a member-versus-leader UI regression test while retaining backend denial tests.
