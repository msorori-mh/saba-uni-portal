# COUNCILS-MODULE-DISCOVERY-01 — تقرير تحليل عمليات بوابة إدارة المجالس الأكاديمية

> مرحلة **تحليل فقط**. لم يُنفَّذ أي تعديل على الكود أو DB أو RLS أو Storage أو Triggers، ولم يُطلق أي نشر جديد، ولم تُستخدم أي بيانات حقيقية أو إرسال إيميلات، ولم يتم توسيع Pilot ولا فتح صفحة `/admin/academic-councils` لأدوار جديدة.

---

## 1. وصف الوحدة

**بوابة إدارة المجالس الأكاديمية** — بوابة رقمية متخصصة لإدارة مجالس الكلية ومجالس الأقسام، تشمل جدولة الاجتماعات، استقبال الموضوعات، إعداد جداول الأعمال، توثيق المحاضر والقرارات، متابعة تنفيذ التوصيات، وأرشفة أعمال المجالس وفق صلاحيات مؤسسية دقيقة.

## 2. نطاق الوحدة

- إدارة مجلس الكلية ومجالس الأقسام داخل كلية تكنولوجيا المعلومات وعلوم الحاسوب.
- الاجتماعات الدورية والاستثنائية.
- دورة حياة الموضوع من مسودة إلى قرار مؤرشف.
- إعداد واعتماد جداول الأعمال والمحاضر.
- توثيق القرارات ومتابعة تنفيذها.
- الأرشفة والتقارير الإدارية.
- المرفقات المؤسسية (مؤيدات، محاضر، قرارات، مستندات تنفيذ).
- التنبيهات داخل البوابة (والبريد الإلكتروني لاحقاً).

## 3. خارج النطاق

- أي علاقة تشغيلية ببوابة الطالب.
- أي علاقة تشغيلية بطلبات شؤون الطلاب.
- الخطط الدراسية، الجداول، إسناد المقررات، التقارير الأكاديمية الحالية.
- بيانات مالية أو موارد بشرية.
- تصويت إلكتروني ملزم قانونياً.
- توقيع إلكتروني معتمد رسمياً.
- مجالس على مستوى الجامعة أو مجالس خارج الكلية.
- استيراد جماعي أو ترحيل بيانات تاريخية في هذه المرحلة.
- إرسال إيميلات فعلية أثناء التأسيس.

## 4. أنواع المجالس

| النوع | الوصف | التكرار المتوقع |
| --- | --- | --- |
| مجلس الكلية | أعلى مجلس داخل الكلية | دوري (شهري مثلاً) |
| مجلس القسم | مجلس مختص بكل قسم أكاديمي | دوري (شهري/نصف شهري) |
| اجتماع استثنائي لمجلس الكلية | خارج الجدولة الدورية | عند الحاجة |
| اجتماع استثنائي لمجلس القسم | خارج الجدولة الدورية | عند الحاجة |

كل مجلس له: `council_type` (`faculty` / `department`)، `department_id` (إلزامي لمجالس الأقسام، `NULL` لمجلس الكلية)، `is_recurring`، `recurrence_rule`.

## 5. الأدوار والصلاحيات المقترحة

### أدوار قائمة يُعاد استخدامها (بلا تعديل حالياً)

- `system_admin`, `admin` — إشراف كامل تقني/مؤسسي.
- `dean` — رئيس مجلس الكلية.
- `department_head` — رئيس مجلس القسم.
- عضو هيئة تدريس (عبر `faculty_profiles` + `departments`) — عضوية محتملة في مجلس قسمه فقط.

### أدوار جديدة مقترحة (لا تُنشأ الآن)

## 6. قيود الوصول (سياسات RLS/UI المقترحة لاحقاً)

- مجلس الكلية: مرئي فقط لعضويات `council_memberships` النشطة على المجلس + `admin/system_admin`.
- مجلس القسم: مرئي فقط لعضويات المجلس على نفس `department_id` + `admin/system_admin`.
- **عزل بين الأقسام**: عضو قسم A لا يرى مجلس قسم B — يُفرض على مستوى RLS بحسب `department_id`.
- **الطلاب**: يُحجب المسار عبر `NAV_ITEM_ROLES` + `canAccessAdminRoute` (قائم فعلياً).
- **الموظفون غير المخولين**: مرفوضون بنفس آلية `/admin/*`.
- **زوار غير مسجلين**: يُحجبون قبل `beforeLoad`.

## 7. دورة الموضوع (Topic Lifecycle)

```
draft → submitted → under_secretary_review
      → needs_more_info (returned to author)
      → accepted_for_agenda | rejected(reason) | deferred(next_meeting)
accepted_for_agenda → in_discussion (during meeting)
                    → decided → closed_archived
```

- كل انتقال يسجل في `topic_events` مع `actor_id`, `from_status`, `to_status`, `reason`, `timestamp`.
- المرفقات (`topic_attachments`) تُرفع في مرحلة draft/submitted.

## 8. دورة الاجتماع (Meeting Lifecycle)

```
scheduled → topics_intake_open → topics_intake_closed
          → agenda_draft → agenda_approved
          → invitations_sent → in_session
          → minutes_draft → minutes_approved
          → closed_archived
```

- كل اجتماع يحمل رقمًا مرجعياً `meeting_number` مسلسل لكل مجلس/سنة.
- الجدولة الاستثنائية تتبع نفس الدورة لكن دون `recurrence_rule`.

## 9. دورة القرار (Decision Lifecycle)

```
drafted (during meeting) → approved (in-session or post-approval)
                          → assigned (to responsible party)
                          → in_execution → executed
                                          → overdue (auto if past due)
                                          → escalated
                          → closed | reopened
```

حقول القرار المقترحة: `decision_number`, `text`, `related_topic_id`, `responsible_entity`, `responsible_user_id?`, `due_date`, `execution_status`, `execution_notes`, `execution_attachments`, `history[]`.

## 10. دورة المتابعة (Follow-up Lifecycle)

- لوحة "قراراتي المطلوب تنفيذها" لكل مستخدم مسؤول.
- تنبيه قبل `due_date` بأيام قابلة للضبط.
- تنبيه تلقائي عند التأخر.
- ربط كل اجتماع جديد بتقرير "متابعة قرارات الاجتماع السابق" كبند إلزامي.

## 11. الجدولة والتنبيهات

| العنصر | المصدر | التعديل |
| --- | --- | --- |
| مجلس الكلية | جدولة دورية (مثال: أول أحد من كل شهر) | admin / مقرر المجلس |
| مجلس القسم | جدولة دورية (يحددها رئيس القسم/المقرر) | admin / رئيس القسم |
| فتح استقبال الموضوعات | X يومًا قبل الاجتماع | إعداد قابل للضبط |
| إغلاق استقبال الموضوعات | Y يومًا قبل الاجتماع | إعداد قابل للضبط |
| تذكيرات الأعضاء | قبل الموعد + قبل إغلاق الاستقبال | إعدادات مجلس |
| إرسال جدول الأعمال | بعد اعتماده | تلقائي |
| تذكيرات القرارات المتأخرة | يومي/أسبوعي | scheduled job لاحقاً |

**قناة التنبيه في MVP**: داخل البوابة فقط (in-app notifications). **البريد الإلكتروني**: لاحقاً وعبر نفس بنية الإيميلات القائمة، ولا يُفعَّل إلا بعد اعتماد صريح.

## 12. الأرشفة والتقارير

- أرشيف الاجتماعات، المحاضر، القرارات.
- بحث حسب: المجلس، القسم، رقم الاجتماع، رقم القرار، الحالة، النطاق الزمني.
- تقارير مقترحة:
  - القرارات غير المنفذة (حسب مجلس/قسم).
  - القرارات المتأخرة (تجاوزت `due_date`).
  - اجتماعات مجلس الكلية (عدد/مواضيع/قرارات).
  - اجتماعات كل قسم.
  - نشاط الأعضاء (حضور، رفع موضوعات).
  - عمر القرارات المفتوحة.

## 13. المرفقات

- أنواع: مؤيدات الموضوع، مسودة المحضر، المحضر المعتمد (PDF)، نص القرار المعتمد، مستندات تنفيذ القرار.
- **Bucket خاص خاص (private)** — لا public URLs مطلقاً.
- Signed URLs قصيرة العمر عند العرض/التحميل.
- Audit لكل فتح/تحميل: `who`, `what`, `when`, `ip`, `user_agent`.
- فحص نوع/حجم الملف قبل الرفع (يُعاد استخدام `storage-validation` القائم).
- حظر تنفيذي على تحميل أنواع خطرة (exe/js/html).

## 14. المخاطر الأمنية

| المخاطرة | الوصف | التخفيف |
| --- | --- | --- |
| Cross-department leakage | عضو يرى مجلس قسم آخر | RLS على `department_id` + عضويات صريحة |
| تسريب محاضر سرية | مرفقات حساسة تصل لغير المخولين | private bucket + signed URLs + audit |
| Public exposure | فهرسة أو مشاركة | `noindex,nofollow`، لا مسارات عامة |
| حذف نهائي لقرار مؤرشف | فقدان مرجعية | منع Hard delete؛ soft delete + audit |
| انتحال هوية المقرر | تعديل محضر بعد الاعتماد | قفل بعد `minutes_approved` + سجل تعديلات |
| Email misuse | إرسال إيميلات فعلية قبل الاعتماد | لا إرسال في MVP؛ Feature flag لاحقاً |
| تسرب بيانات هيئة التدريس | استعلامات مفتوحة | استخدام `has_role` + عضويات المجالس |
| تلاعب بالقرار بعد الاعتماد | تحرير خفي | Immutable fields + `decision_history` |
| Privilege escalation | إعطاء عضوية غير مؤهلة | إدارة العضويات محصورة على admin/dean |
| Audit gap | عدم توثيق العمليات | Trigger لكل تعديل ينشئ سجلاً |

## 15. المتطلبات المعمارية (لاحقة، غير مُنفَّذة الآن)

- **Client**: مسارات فرعية تحت `/admin/academic-councils/` (لوحة، اجتماعاتي، جدول أعمال، محضر، قرارات، أرشيف، إعدادات).
- **Server functions** (`*.functions.ts`) لكل عملية كتابة، محمية بـ `requireSupabaseAuth` + `has_role` أو فحص عضوية المجلس.
- **جداول DB مقترحة** (تسمية أولية):
  - `councils` (type, department_id, name_ar, is_active, recurrence_rule, settings)
  - `council_memberships` (council_id, user_id, role_in_council, active_from, active_to)
  - `council_meetings` (council_id, meeting_number, kind, scheduled_at, status, intake_opens_at, intake_closes_at)
  - `council_topics` (meeting_id, submitted_by, title, body, status, decision_id?)
  - `council_topic_events` (topic_id, actor_id, from_status, to_status, note, at)
  - `council_agenda_items` (meeting_id, topic_id, order_no, approved)
  - `council_minutes` (meeting_id, body, drafted_by, approved_by, approved_at, locked)
  - `council_decisions` (topic_id, decision_number, text, responsible_user_id, responsible_entity, due_date, execution_status)
  - `council_decision_history` (decision_id, actor_id, change_type, old_value, new_value, at)
  - `council_attachments` (owner_type, owner_id, storage_path, mime, size, uploaded_by)
  - `council_notifications` (user_id, council_id, meeting_id?, kind, payload, read_at)
  - `council_audit_log` (actor_id, target_type, target_id, action, meta, at)
- **RLS** لكل جدول: قراءة/كتابة بحسب عضوية المجلس + دور المستخدم + `department_id` للأقسام.
- **Storage**: bucket خاص `council-attachments` (private) + سياسات وصول عبر signed URLs من server functions.
- **Triggers**: `updated_at`, `decision_history`, `council_audit_log`, ترقيم مسلسل للاجتماعات/القرارات.
- **Jobs**: مهام مجدولة لتذكيرات القرارات المتأخرة (يمكن الاستفادة من نفس نمط `automation.functions.ts`).
- **Email**: يبقى معطلاً افتراضياً؛ عند التفعيل يستخدم نفس بنية `email.functions.ts` + قوالب مخصصة.

## 16. العلاقة مع البنية الحالية

- **الأقسام** (`departments`): مصدر `department_id` لمجالس الأقسام.
- **هيئة التدريس** (`faculty_profiles`): مصدر بيانات الأعضاء وربطهم بأقسامهم.
- **المستخدمون والأدوار** (`user_roles`, `has_role`): يُعاد استخدام نمط RBAC القائم دون تعديل الأدوار الحالية.
- **بوابة الطالب / شؤون الطلاب / التقارير / الخطط**: **لا تأثر مطلقاً** — الوحدة معزولة.
- **Pilot الحالي**: **لا تأثر**؛ الصفحة الحالية مبدئية ومحصورة على 3 أدوار إشرافية.
- **نمط `admin-nav.ts`**: يستوعب إضافة مسارات فرعية داخل نفس المجموعة لاحقاً.

## 18. المخاطر المتبقية على مستوى التحليل

- منخفضة. المرحلة تحليلية بالكامل ولم تلامس الإنتاج.
- خطر واحد إدراكي: قد يُظن أن التحليل كافٍ للانتقال مباشرة للتنفيذ — يُخفَّف بإلزام مرحلة `COUNCILS-MODULE-DESIGN-01` قبل أي migration.

## 19. التوصية للمرحلة التالية

**`COUNCILS-MODULE-DESIGN-01`** — تصميم تفصيلي يشمل:

1. ERD نهائي للجداول أعلاه.
2. سياسات RLS مصاغة كـ SQL جاهزة للمراجعة (بدون تطبيق).
3. تصميم شاشات مفصل لكل مسار فرعي.
4. سياسات المرفقات وأسماء الـ buckets.
5. مخطط التنبيهات (in-app أولاً، بريد لاحقاً خلف feature flag).
6. خطة MVP على دفعات: (أ) هيكل البيانات + RLS، (ب) عضويات + عرض المجالس، (ج) موضوعات + جدول أعمال، (د) محاضر + قرارات، (هـ) متابعة + أرشيف + تقارير.
7. خطة اختبار أمني مسبقة (cross-department، escalation، leakage).
