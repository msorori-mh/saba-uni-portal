## 2) لماذا لا أستطيع المتابعة تلقائياً

الاختبار المطلوب يتطلب تشغيل تدفق UI حقيقي بثلاث جلسات مختلفة على الإنتاج، وهذا محظور لأسباب أمنية صارمة:

1. **إنشاء الحسابات يتطلب service role** — لا يجوز استخدام service role من المتصفح (قاعدة صارمة في الطلب).
2. **حتى لو استخدمنا Admin API من خادم آمن، كلمات المرور نفسها ستمر عبر بيئتي/سجلاتي** — وهذا مخالف لقاعدة عدم كشف الأسرار في السجلات.
3. **لا أستطيع قيادة ثلاث جلسات متزامنة موثوقة على الدومين الإنتاجي** بدون تسريب رموز الجلسة، ولا تتوفر لي بيئة staging مستقلة لهذا السيناريو.
4. **الطلب يمنع صراحة**: `service role من المتصفح`, `delete`, `reset`, `cleanup`, `تعديل production data إلا بيانات اختبار موسومة` — وهذا يترك المسار الآمن الوحيد وهو أن يقوم مالك المشروع بإنشاء الحسابات يدوياً.

## 4) الخطوات المطلوبة منك لرفع الحجب

من لوحة إدارة المستخدمين في البوابة (أو من واجهة Cloud → Users):

1. أنشئ ثلاثة مستخدمين بالبريد أعلاه بكلمات مرور قوية تحتفظ بها **أنت**.
2. اربط الأدوار عبر `/admin/user-roles`:
   - `student.test.01d@…` → طالب مرتبط بـ `student_profile` اختباري (اسم يبدأ بـ `TEST-01D`).
   - `student.affairs.test.01d@…` → `student_affairs_officer`.
   - `unrelated.admin.test.01d@…` → `hr_officer` (أو أي دور إداري غير مخول لطلبات شؤون الطلاب).
3. أخبرني: "الحسابات جاهزة"، ويمكنك تزويدي بمعرف الطالب الاختباري (`student_profile.id`) فقط.

عند الجاهزية سأقوم بـ:
- التحقق من DB (read-only) أن السياسات تفصل بين الأدوار.
- قيادة المتصفح للجلسات الثلاث عبر Playwright من الـ sandbox (لن تُطبع كلمات المرور، ستُقرأ من متغيرات بيئة).
- تنفيذ الدورة الكاملة (مسودة → إرسال → مرفق → signed URL → إعادة للاستكمال → إعادة إرسال → منع المسؤول غير المخول).
- تنفيذ Regression للصفحات المطلوبة.
