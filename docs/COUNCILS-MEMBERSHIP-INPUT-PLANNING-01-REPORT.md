## 1. مصادر البيانات التي تمت مراجعتها

| المصدر | الحالة | الفائدة |
|--------|--------|--------|
| `user_roles` (enum `app_role`) | متوفر | 1 dean، 2 admin، 2 system_admin — بلا staff_profile مربوط |
| `staff_profiles` (user_id, department_id, job_title, role_type) | متوفر بنيوياً | **فارغ لأصحاب الأدوار الإدارية** — لا اسم/قسم/وظيفة مربوطة بالـ user_ids الحالية |
| `faculty` (لا user_id) | متوفر (33 صف تقريباً) | مرجع أسماء عرض فقط — بدون user_id لا يصلح لعضوية |
| `faculty_profiles` (user_id, faculty_id, department_id, academic_rank) | 33 صف بـ user_id | مصدر واقعي لهيئة التدريس المرتبطين بحسابات |
| `organizational_positions` (dean, vice_dean_academic, vice_dean_students, college_secretary…) | معرَّفة كمناصب | **بلا `position_assignments` نشطة** — لا شخص مربوط بأي منصب |
| `position_assignments` | فارغ نشطاً | لا يوجد إسناد يربط user_id بمنصب |
| `departments` | 3 أقسام نشطة (IT، CS، IS) | مرجعي |
| `academic_council_members` (البنية والسياسات) | جاهزة | INSERT يتطلب `can_manage_council(auth.uid(), council_id)` + `created_by = auth.uid()` → seed مباشر عبر service role يعمل، لكن لا تنطبق سياسات المستخدم |

**قيود بنيوية مهمة:**
- `academic_council_members.user_id` FK إلى `auth.users` → **لا عضوية بلا حساب مصادقة فعلي**.
- `member_role` enum: `chair / vice_chair / secretary / member / viewer`.
- قيد فريد: `(council_id, user_id, member_role, active_from)` → آمن للتشغيل idempotent.

### MISSING_USER_ID (لا يمكن إضافتهم الآن)

| الدور المطلوب | لماذا مفقود |
|----------------|-------------|
| نائب العميد للشؤون الأكاديمية | لا `position_assignments` نشط، ولا حساب بدور مطابق |
| نائب العميد لشؤون الطلاب | نفس السبب |
| أمين الكلية / مقرر المجلس | لا user_id مؤكد؛ لا حساب بدور `secretary` مربوط بالمنصب |

### AMBIGUOUS

- 33 صفاً في `faculty_profiles` بـ user_id لكن **لا يوجد ما يميّز من هو رئيس القسم**، لأن `faculty_profiles` لا يحمل حقل "رئيس قسم" ولا إسناد فعّال في `position_assignments`.

## 3. البيانات الناقصة (يجب تأكيدها منك)

1. **العميد المؤكد:** هل `72e93a64-…e769` هو فعلاً د. العميد؟ ما اسمه الكامل وبريده؟
2. **نواب العميد:** الأسماء + user_ids (أو حسابات لإنشائها لاحقاً في مرحلة منفصلة).
3. **مقرر / أمين مجلس الكلية:** الاسم + user_id.
4. **رؤساء الأقسام الثلاثة:** لكل قسم (IT / CS / IS): الاسم + user_id.
5. **نطاق الأعضاء:** رؤساء الأقسام فقط، أم إضافة ممثلي هيئة التدريس؟
6. **مواءمة `organizational_positions` + `position_assignments`:** هل نملأها كمصدر واحد (single source of truth) قبل عضوية المجلس؟

## 4. خيارات الإدخال المقترحة (بدون تنفيذ)

| الخيار | المحتوى | متطلبات | الجاهزية |
|--------|--------|---------|----------|
| **A** | العميد فقط كـ chair | user_id للعميد مؤكد | جاهز نظرياً، ينقص تأكيدك للاسم/البريد |
| **B** | العميد (chair) + مقرر المجلس (secretary) | user_id لكليهما | غير جاهز — مقرر المجلس مفقود |
| **C** | العميد + مقرر + رؤساء الأقسام (members) | user_ids لخمسة أشخاص + ربط قسم | غير جاهز — بيانات رؤساء الأقسام مفقودة كلياً |
| **D** | إضافة عضويات موسّعة عبر شاشة إدارة داخل `/admin/academic-councils` | بناء UI مسؤول + سياسات كتابة (موجودة أصلاً في RLS) | يتطلب موافقة صريحة على تفعيل شاشة الكتابة |

## 5. المخاطر

| المخاطرة | الشدة | التخفيف |
|----------|-------|---------|
| user_id غير صحيح يُربط بمنصب حساس | عالية | لا إدخال بدون تأكيدك الصريح لكل user_id |
| تعيين شخص في `chair` وهو ليس العميد | عالية | تأكيد كتابي منك قبل seed |
| ازدواج صلاحيات: `admin`/`system_admin` كأعضاء مجلس يخلق التباساً في السياسات | متوسطة | استبعادهم افتراضياً إلا بطلبك |
| نقص رؤساء الأقسام كلياً | عالية | إما تعبئة `position_assignments` أولاً، أو إرجاء الخيار C |
| seed يدوي متكرر بدون UI يجعل الصيانة هشّة | متوسطة | بناء شاشة إدارة عضويات قبل التوسع (D) |
| القيد `created_by = auth.uid()` في `INSERT policy` يعني seed عبر service role يتجاوز السياسة (يعمل لكن يفوّت التدقيق التطبيقي) | منخفضة–متوسطة | تفضيل الإدخال من داخل UI لمستخدم مخوَّل بعد الجاهزية |

## 6. الإجابات المطلوبة

- هل يمكن إضافة عضويات آمنة الآن؟ **لا** — لا يوجد ولو مرشح واحد بمستوى CONFIRMED كامل (اسم + بريد + منصب موثَّق).
- هل يُوصى ببناء شاشة إدارة عضويات قبل الإضافة؟ **نعم — مع تحفّظ**: يمكن أيضاً تنفيذ Option A محدود جداً (العميد فقط كـ chair) فور تأكيدك للـ user_id والاسم، دون انتظار UI. لكن للتوسع (B/C/D) شاشة الإدارة أنظف وأكثر أماناً.

## 7. التوصية

**NEEDS_USER_INPUT** — قبل أي seed لعضويات، يلزم منك:

1. تأكيد user_id للعميد + اسمه الكامل.
2. تحديد ما إذا كنت تريد Option A فوراً (عميد فقط) بعد تأكيده.
3. لتوسيع لاحقاً (B/C): تزويد user_ids لمقرر المجلس ورؤساء الأقسام، أو الموافقة على مسار BUILD_ADMIN_MEMBERSHIP_UI_FIRST.
